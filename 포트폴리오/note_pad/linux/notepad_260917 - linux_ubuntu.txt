#### Swagger(스웨거)

- API를 설명하고 확인하기 위한 문서·도구이다.(API 명세 / API 문서 / API 테스트)
- 서버가 제공하는 API의 사용 방법을 문서로 보여주고 직접 요청을 테스트할 수 있게 해주는 도구이다.(무언가를 설명하는 설명서·명세서이다.)
- Swagger를 사용하면 이러한 API 정보를 웹 화면에서 확인하고, 직접 요청을 보내 결과까지 확인할 수 있다.

---

#### Postman(포스트맨 = 우편 배달원)

- 서버에 요청을 보내고 응답을 확인하는 도구이다.(API 요청 / API 테스트)
- 서버에 HTTP 요청을 보내고 서버의 응답을 확인하는 API 테스트 도구이다.
- URL을 보내면, Postman에서 보내면 서버가 반환하는 JSON 응답을 바로 확인할 수 있다.

#### enums(열거 / 정해진 값 / 선택지)

- 정해진 값들을 열거해 놓은 것이다.
- 사용할 수 있는 정해진 값들을 미리 정의해 놓은 자료형이다.
- 미리 정해진 선택지를 사용하는 것이 Enum이다.

#### DTO / Model / Entity

```
DTO = 전달(Transfer)
→ 데이터를 다른 곳으로 전달하는 것
```

```
Model = 표현(Model)
→ 데이터를 어떤 형태로 표현하는 것
```

```
Entity = 실체(Entity)
→ 실제 대상이나 개체를 표현하는 것
```

---

#### DAO / Repository = 데이터 접근(Data Access)

```
DAO(Data Access Object)
→ Access = 접근 → "데이터에 접근하는 객체"
```

```
Repository = 저장소 / 보관소
→ "데이터를 저장하고 꺼내는 역할"
```

#### **🏥 예시) 병원 시스템**

> **👤 Client(환자)  —{{진료 신청}}→   🪟 View(접수 화면) →

→  👩‍💼 Controller(접수 담당자)  —{{DTO("환자 정보가 담긴 신청서")}}→

→  👨‍⚕️ Service(의사)  —{{진료/업무 판단}}→  

→  📋 DAO 또는 💻 Repository(기록 담당자)  —{{Entity("병원 공식 기록")}}→

→  🗄️ DB(병원 전산 기록실)

⚙️ Config(병원 운영 규칙 / 보안 설정)
🏷️ Enum(대기 / 진료 중 / 완료 같은 정해진 상태값)
📦 Model(화면이나 업무에서 사용하는 데이터 묶음)**
> 

#### **환자(Client)가 접수 화면(View)을 통해 요청하면,
접수 담당자(Controller)가 진료 의사(Service)에게 전달하고,
의사는 기록 담당자(DAO/Repository)를 통해
공식 환자 기록(Entity)을 DB에서 조회 및 저장하며,
DTO는 그 과정에서 데이터를 전달하는 서류이고,
Model은 Controller가 View에 보여줄 데이터 담고 전달하는 묶음이며,
Config는 병원 시스템의 운영 규칙이고,
Enum은 병원 시스템의 정해진 상태값이라고 할 수 있다.**

| 개발 구성요소 | 병원 비유 | 핵심 역할 |
| --- | --- | --- |
| Client | 👤 환자 | 서비스를 요청 |
| View | 🪟 접수/결과 화면 | 사용자에게 화면 제공 |
| Controller | 👩‍💼 접수 담당자 | 요청을 받고 Service에 전달 |
| Service | 👨‍⚕️ 의사 | 업무/비즈니스 로직 처리 |
| DAO | 📋 기록 담당자 | DB 접근 |
| Repository | 💻 전산 기록 담당자 | DB 접근 |
| DTO | 📝 환자가 제출하는 서류 | 계층 간 데이터 전달 |
| Entity | 📄 공식 환자 기록 | DB 데이터를 객체로 표현 |
| Model | 📦 업무 데이터 상자 | 문맥에 따라 데이터 전달/표현 |
| View | 🖥️ 진료 결과 화면 | 사용자에게 결과 표시 |
| Config | ⚙️ 병원 운영 규칙 | 시스템 설정 |
| Enum | 🏷️ 진료 상태표 | 정해진 값 표현 |
| DB | 🗄️ 병원 기록 보관실 | 실제 데이터 저장 |

## .gitignore 설정 방식: 블랙리스트 vs 화이트리스트

#### 1. 블랙리스트 방식 (제외할 것만 명시)

- 가장 일반적이고 흔하게 쓰는 방식이다.
- 무시할 파일/폴더를 하나씩 나열한다.
- 블랙리스트 예시

```
.log
*.class
node_modules/
target/
.env
.idea/
*.tmp
build/
```

| 패턴 | 의미 |
| --- | --- |
| *.log | 확장자가 .log인 모든 파일을 무시한다. |
| node_modules/ | 해당 폴더 전체를 무시한다. |
| .env | 특정 파일명을 무시 (환경변수, 민감정보) |
| build/, target/ | 빌드 결과물 폴더를 무시한다. |

#### 2. 화이트리스트 방식 (`!`로 예외 지정 — 허용할 것만 명시)

- ! 기호로 예외를 지정하는 방식이다.
- 프로젝트 구조가 복잡하거나 관리할 파일이 명확히 정해져 있을 때 사용한다.
- 화이트리스트 예시

```
1. 일단 모든 파일 무시
*

2. 특정 파일/폴더는 예외로 허용
!.gitignore
!src/
!src/**
!README.md
!pom.xml
```

| 패턴 | 의미 |
| --- | --- |
| * | 모든 파일을 일단 무시 대상으로 지정한다. |
| !src/ | src 폴더는 예외하고, 추적을 허용한다. |
| !src/** | src 폴더 내부의 모든 파일을 예외 처리한다.(주의: !src/만 쓰면 폴더는 보여도 내부 파일은 여전히 무시될 수 있음) |
| !.gitignore | .gitignore 파일 자체는 항상 추적되게 한다. |

#### 3. 주의할 점 — 화이트리스트 방식의 함정

- Git은 이미 무시된(ignored) 디렉토리 내부는 기본적으로 들여다보지 않는다.
- 그래서 아래처럼 작성하면 의도대로 동작하지 않을 수 있다.
- 해결 방법: 상위 폴더들도 하나씩 예외 처리해줘야 한다.

```
!src/
!src/main/
!src/main/java/
!src/main/java/**
```

#### @RestController 란?

- Spring MVC에서 사용하는 어노테이션으로, @Controller + @ResponseBody를 합친 것이다.
- 클래스에 붙이면 해당 클래스의 모든 핸들러 메서드가 반환하는 객체가 자동으로 JSON(또는 XML)으로 직렬화되어 HTTP 응답 본문에 담긴다.
- 즉, View(JSP, Thymeleaf 등)를 반환하지 않고 데이터 자체를 반환하는 REST API 컨트롤러를 만들 때 사용한다.

!image.png

#### @Transactional 이란?

- 메서드나 클래스에 붙이면 해당 로직을 하나의 트랜잭션 단위로 묶어준다.
- 메서드 실행 중 예외(기본적으로 RuntimeException, Error)가 발생하면 자동으로 롤백, 정상 종료되면 커밋된다.
- 여러 DB 작업(예: 계좌 이체처럼 A 차감 + B 증가)을 원자적으로 처리해야 할 때 필수이다.

#### @NotBlank 란?

- Bean Validation(JSR-380) 어노테이션 중 하나로, 문자열 필드가 null이 아니고, 공백만으로 이루어지지 않아야 하는 것을 검증한다.
- "", " ", null 모두 유효하지 않은 값으로 처리된다.

#### @Size 란?

- 문자열, 배열, 컬렉션 등의 길이(크기)를 제한할 때 사용한다.
- min, max 속성으로 범위를 지정한다.

#### @Email 이란?

- 문자열이 이메일 형식(예: example@domain.com)을 따르는지 검증한다.
- null은 유효한 것으로 취급되므로(빈 값 허용), null 자체를 막으려면 @NotBlank나 @NotNull과 함께 사용해야 한다.

!image.png

!image.png

#### @Entity 란?

- JPA(Java Persistence API)에서 해당 클래스가 데이터베이스 테이블과 매핑되는 엔티티임을 나타낸다.
- 클래스의 인스턴스가 테이블의 한 행(row)에 대응된다.
- 보통 @Id(기본키), @GeneratedValue(자동 생성 전략) 등과 함께 사용된다.

#### curl(Client URL) 이란?

- 커맨드라인에서 URL을 이용해 서버와 데이터를 주고받을 수 있는 도구이다.
- HTTP, HTTPS, FTP 등 다양한 프로토콜을 지원하며, 특히 REST API를 테스트하거나 서버에 요청을 보낼 때 많이 사용된다.
- GET 요청

```bash
curl http://localhost:8080/api/users
```

- GET 요청 + 응답 헤더까지 보기

```bash
curl -i http://localhost:8080/api/users
```

- 특정 ID 조회

```bash
curl http://localhost:8080/api/users/1
```

- POST 요청 (데이터 전송)

```bash
curl -X POST http://localhost:8080/api/users \  -H "Content-Type: application/json" \  -d '{"name": "홍길동", "email": "hong@example.com"}'
```

## HTTP 상태 코드(Status Code) 100번대~500번대

- HTTP 상태 코드는 첫 자리 숫자에 따라 5개 그룹으로 나뉜다.

| 100번대~500번대 | 의미 |
| --- | --- |
| 1xx | 정보성 |
| 2xx | 성공 |
| 3xx | 리다이렉션 |
| 4xx | 클라이언트 오류 |
| 5xx | 서버 오류 |

---

#### 1xx (정보성, Informational)

- 요청을 받았고 처리 중이라는 의미. 클라이언트는 계속 요청을 진행하면 된다.

| 코드 | 의미 |
| --- | --- |
| 100 | Continue - 요청이 계속 진행 가능하다. |
| 101 | Switching Protocols - 프로토콜을 전환한다.
(예: WebSocket) |

---

#### 2xx (성공, Success)

- 요청이 성공적으로 처리된다.

| 코드 | 의미 |
| --- | --- |
| 200 | OK - 요청이 성공했다. |
| 201 | Created - 리소스 생성을 성공했다.
(POST 요청 후 흔히 사용) |
| 204 | No Content - 성공했지만 응답 본문이 없다.
(DELETE 등) |

---

#### 3xx (리다이렉션, Redirection)

- 요청을 완료하려면 추가 작업(다른 URL로 이동 등)이 필요하다.

| 코드 | 의미 |
| --- | --- |
| 301 | Moved Permanently - 영구적으로 이동했다. |
| 302 | Found - 임시로 이동했다. |
| 304 | Not Modified - 캐시된 데이터를 그대로 사용 가능하다. |

---

#### 4xx (클라이언트 오류, Client Error)

- 클라이언트(요청 보낸 쪽)의 잘못으로 요청이 처리되지 않는다.

| 코드 | 의미 |
| --- | --- |
| 400 | Bad Request - 잘못된 요청이다.
(예: @NotBlank, @Email 검증 실패 시) |
| 401 | Unauthorized - 인증이 필요하다.
(로그인 안 됨) |
| 403 | Forbidden - 인증은 됐지만 권한이 없다. |
| 404 | Not Found - 리소스를 찾을 수 없다. |
| 405 | Method Not Allowed - 허용되지 않은 HTTP 메서드이다. |
| 409 | Conflict - 리소스가 충돌했다.(예: 중복 데이터) |

---

#### 5xx (서버 오류, Server Error)

- 서버 쪽의 잘못으로 요청을 처리하지 못한다.
- 클라이언트는 제대로 보냈는데 서버에서 문제가 발생했다.

| 코드 | 의미 |
| --- | --- |
| 500 | Internal Server Error - 서버 내부에 오류가 발생했다.(가장 흔함, 예외 처리 안 된 경우) |
| 502 | Bad Gateway - 게이트웨이/프록시가 잘못된 응답을 받았다. |
| 503 | Service Unavailable - 서버 과부하 또는 점검 중 |
| 504 | Gateway Timeout - 게이트웨이가 응답 시간을 초과했다. |
