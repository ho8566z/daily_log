## 취업을 위한 필요 능력

1. 성실성
    - 맡은 일을 꾸준히 수행하고, 정해진 일정과 약속을 지키는 태도이다.
2. 책임감
    - 자신이 맡은 작업의 결과에 책임을 지고, 문제가 생기면 원인을 확인하고 해결하려는 태도이다.
3. 협업과 소통 능력
    - 팀원과 요구사항, 진행 상황, 문제점을 공유하고 서로의 작업을 연결하는 능력이다.
4. 적응력과 유연성
    - 새로운 기술, 개발 환경, 요구사항의 변화에 맞춰 학습하고 대응하는 능력이다.

## 동기(Synchronous) 방식 이란?

- 요청을 보낸 후, 응답이 올 때까지 다음 코드를 실행하지 않고 대기(block)하는 방식이다.
- 작업이 순서대로(순차적으로) 처리되기 때문에 코드 흐름을 이해하기 쉽지만, 응답이 오래 걸리는 작업이 있으면 그 뒤의 작업들도 전부 지연된다.

---

## 비동기(Asynchronous) 방식 이란?

- 요청을 보낸 후 응답을 기다리지 않고, 그동안 다른 작업을 계속 수행하는 방식이다.
- 작업이 끝나면 콜백, 이벤트, Promise, async/await 등으로 결과를 받아 처리한다.

#### 블로킹(Blocking)과 논블로킹(Non-blocking)

- 동기/비동기와 자주 섞이지만, 보는 관점이 다른 개념이다.
    - 블로킹/논블로킹은 호출된 쪽이 제어권을 바로 돌려주는지를 본다.
    - 동기/비동기는 호출한 쪽이 결과를 직접 챙기는지, 나중에 통보받는지를 본다.

---

## 동기 VS. 비동기

| 구분 | 동기(Synchronous) | 비동기(Asynchronous) |
| --- | --- | --- |
| 기다림 | 응답이 올 때까지 기다린 후 다음 작업을 진행한다. | 응답을 기다리지 않고 다음 작업을 진행한다. |
| 결과 처리 | 호출한 쪽이 결과를 직접 받아 처리한다. | 완료되면 콜백/이벤트로 통보받아 처리한다. |

#### 동기/비동기 + 블로킹/논블로킹 조합

| 구분 | 동작 |
| --- | --- |
| 동기 + 블로킹 | 끝날 때까지 멈춰서 기다린 뒤 결과를 직접 처리한다. (가장 흔하고 단순) |
| 동기 + 논블로킹 | 제어권은 바로 돌려받지만, 끝났는지 계속 직접 확인(polling)한다. |
| 비동기 + 논블로킹 | 제어권을 바로 돌려받고, 끝나면 콜백/이벤트로 통보받는다. (Node.js 등) |
| 비동기 + 블로킹 | 비동기로 만들었지만 결국 기다리며 멈추는 경우로, 성능 저하의 원인이 된다. |

---

## Stateful (상태 유지) 이란?

- 서버가 클라이언트의 이전 요청 상태를 저장해 두고, 다음 요청에 활용하는 방식이다.
- 예시로 세션 기반 로그인, WebSocket 연결 등이 있다.

#### Stateful의 핵심 특징

- 서버가 상태를 저장
    - 같은 사용자의 다음 요청에서, 서버가 저장해 둔 이전 상태를 그대로 활용할 수 있다.
- 통제가 쉬움
    - 서버가 상태를 쥐고 있으므로, 강제 로그아웃처럼 상태를 즉시 바꾸는 작업이 쉽다.
- 서버 확장이 어려움
    - 서버가 여러 대면 상태를 공유해야 하므로, Redis 같은 공용 저장소가 필요하다.

---

## Stateless (무상태) 이란?

- 서버가 이전 요청을 기억하지 않고, 각 요청을 독립적으로 처리하는 방식이다.
- 예시로 토큰(JWT) 기반 인증, HTTP 프로토콜 자체 등이 있다.

#### Stateless의 핵심 특징

- 요청마다 필요한 정보를 함께 전달
    - 서버가 기억하지 않으므로, 클라이언트가 요청마다 인증 정보 등을 직접 보낸다.
- 서버 확장이 쉬움
    - 어느 서버가 요청을 받아도 똑같이 처리할 수 있다.
- 강제 만료가 어려움
    - 이미 발급한 토큰은 만료 시간 전까지 유효하므로, 로그아웃이나 계정 탈취에 즉시 대응하기 어렵다.
    - 이를 막으려고 블랙리스트나 리프레시 토큰 저장소를 서버에 두면, 그 부분은 다시 Stateful이 된다.

---

## Stateful VS. Stateless

| 구분 | Stateful | Stateless |
| --- | --- | --- |
| 상태 저장 | 서버가 저장한다. | 서버가 저장하지 않는다. |
| 요청 처리 | 이전 상태를 이어서 처리한다. | 각 요청을 독립적으로 처리한다. |
| 서버 확장 | 상태 공유가 필요해 어렵다. | 어느 서버든 처리 가능해 쉽다. |
| 강제 만료 | 쉽다. | 어렵다. |
| 대표 예 | 세션, WebSocket | 토큰(JWT), HTTP |

---

## 세션(Session) 이란?

- 로그인에 성공하면 서버가 사용자 상태를 세션 저장소에 저장하고, 클라이언트에게는 세션 ID만 쿠키로 내려주는 인증 방식이다.
- 이후 요청마다 클라이언트가 세션 ID를 보내면, 서버가 저장소에서 조회해 사용자를 확인한다.

```
브라우저
│
│ 로그인 (아이디 / 비밀번호)
▼
서버 ────────► 세션 저장소에 { 세션 ID : 사용자 정보 } 저장
│
│ Set-Cookie: SESSIONID=abc123
▼
브라우저
이후 요청
│
│ Cookie: SESSIONID=abc123
▼
서버 ────────► 세션 저장소에서 abc123 조회
│
▼
사용자 확인
```

#### 대표적인 예:

- 전통적인 웹 서비스(JSP, Spring MVC + Thymeleaf)
- 관리자 페이지

---

## 토큰(Token) 이란?

- 로그인에 성공하면 서버가 인증 정보를 담은 토큰을 비밀키로 서명해서 발급하고, 서버는 따로 저장하지 않는 인증 방식이다.
- 이후 요청마다 클라이언트가 토큰을 보내면, 서버는 서명과 만료 시간만 검증해 사용자를 확인한다.

```
브라우저
│
│ 로그인 (아이디 / 비밀번호)
▼
서버 ────────► JWT 생성 후 비밀키로 서명 (저장하지 않음)
│
│ JWT 발급
▼
브라우저
이후 요청
│
│ Authorization: Bearer <JWT>
▼
서버 ────────► 서명 검증 + 만료 시간 확인 (저장소 조회 없음)
│
▼
사용자 확인
```

#### 대표적인 예:

- 모바일 앱
- REST API 서버
- 마이크로서비스

---

## 세션 VS. 토큰

| 구분 | 세션 | 토큰(JWT) |
| --- | --- | --- |
| 상태 저장 위치 | 서버(세션 저장소) | 클라이언트(토큰 안에 정보 포함) |
| 방식 | Stateful | Stateless |
| 요청 시 서버 동작 | 세션 ID로 저장소를 조회한다. | 서명을 검증한다. (조회 불필요) |
| 서버 확장 | 세션 공유가 필요하다. (Redis 등) | 검증만 하면 되므로 쉽다. |
| 강제 로그아웃 | 세션을 삭제하면 즉시 무효화된다. | 만료 전까지 유효하므로 별도 보완책이 필요하다. |
| 전송 데이터 크기 | 세션 ID만 보내서 작다. | Claim이 늘수록 커진다. |
| 적합한 서비스 | 전통적인 웹 서비스, 관리자 페이지 | 모바일 앱, REST API, 마이크로서비스 |

## JWT(JSON Web Token) 이란?

- Header, Payload, Signature 세 부분을 점(.)으로 이어 붙인 토큰 형식이다.
- 각 부분은 Base64URL로 인코딩되어 있다.

```
Header.Payload.Signature
```

#### JWT의 구성

- Header
    - 토큰의 타입과 서명 알고리즘을 담는다. (예: { "alg": "HS256", "typ": "JWT" })
- Payload
    - 사용자 식별자, 권한, 만료 시간 등의 Claim을 담는다.
    - 자주 쓰는 Claim으로 sub(사용자 식별자), iat(발급 시각), exp(만료 시각)가 있다.
- Signature
    - Header와 Payload를 비밀키(secret key)로 서명한 값이다.
    - 서버는 같은 비밀키로 서명을 다시 계산해 비교하고, 토큰 내용이 바뀌었는지(변조) 확인한다.
    - 비밀키는 서버만 갖고 있으며, 토큰 안에 들어가지 않는다.

#### Payload에 민감 정보를 넣으면 안 되는 이유

- Payload는 암호화가 아니라 Base64URL 인코딩일 뿐이라, 토큰을 가진 누구나 디코딩해서 읽을 수 있다.
- Signature는 변조를 막을 뿐, 내용을 숨기지 않는다.
- 따라서 비밀번호 같은 민감 정보는 넣지 않고, exp로 유효 기간을 반드시 제한한다.

## 액세스 토큰(Access Token) & 리프레시 토큰(Refresh Token) 이란?

- 토큰이 탈취됐을 때의 피해를 줄이려고, 역할과 유효 기간이 다른 토큰 두 개를 나눠 쓰는 방식이다.

```
브라우저
│
│ Access Token
▼
서버 ────────► API 요청 정상 처리
(Access Token 만료)
│
│ Refresh Token
▼
서버 ────────► 검증 후 새 Access Token 발급
```

#### 액세스 토큰과 리프레시 토큰의 핵심 특징

- 액세스 토큰
    - API 요청 인증에 사용하며, 유효 기간을 짧게(예: 15분~1시간) 둔다.
    - 탈취되더라도 피해 시간을 줄이기 위함이다.
- 리프레시 토큰
    - 액세스 토큰이 만료되었을 때, 새 액세스 토큰을 발급받는 용도로만 쓴다.
    - 유효 기간을 길게(예: 2주) 두고, 서버에 저장해 두면 로그아웃·강제 만료를 처리할 수 있다.

#### 토큰 저장 위치

- 쿠키(HttpOnly, Secure, SameSite)
    - JavaScript로 읽을 수 없어 XSS 탈취에 강하지만, 요청에 자동으로 포함되므로 CSRF 대비가 필요하다.
- localStorage / sessionStorage
    - 구현이 간단하지만, XSS가 발생하면 토큰이 그대로 탈취된다.
- XSS는 공격자의 스크립트가 사용자 브라우저에서 실행되는 공격이고, CSRF는 로그인된 상태를 악용해 사용자가 원치 않는 요청을 보내게 하는 공격이다.

## 수업 필기의 관계 정리

```
sync  - stateful  - 세션 - 동기 방식
async - stateless - 토큰 - 비동기 방식
  └ header, payload, signature(secret key)
```

#### 1. 세 쌍은 서로 다른 층위의 개념

| 구분 | 정체 |
| --- | --- |
| 동기 / 비동기 | 작업을 처리하는 방식 |
| Stateful / Stateless | 서버가 클라이언트의 상태를 기억하는지 |
| 세션 / 토큰 | 로그인(인증) 상태를 관리하는 방법 |
- 세션 = Stateful, 토큰(JWT) = Stateless는 맞는 연결이다.
- 세션 = 동기, 토큰 = 비동기는 정의상 관계가 없다.

---

#### 2. 그럼에도 같은 줄로 묶이는 이유는?

- 1줄(sync - stateful - 세션)
    - 전통적인 웹 서버(JSP, Spring MVC)는 요청을 순서대로 기다리며 처리했고(동기), 서버가 화면(HTML)을 만들어 주는 MPA 구조라 로그인 상태도 세션으로 기억했다.
- 2줄(async - stateless - 토큰)
    - SPA·모바일 앱이 API를 비동기로 호출하고 서버를 여러 대로 늘리면서, 저장소 조회 없이 서명만 검증하는 토큰이 잘 맞았다.

---

#### 3. 반례

| 구분 | 실제 예 |
| --- | --- |
| 세션 + 비동기 | Node.js(Express)의 express-session, Spring WebFlux의 WebSession |
| 토큰 + 동기 | Spring MVC(Spring Boot 기본) + JWT 필터 |
| Stateful + 비동기 | WebSocket 채팅 |
| Stateless + 동기 | HTTP의 기본 요청-응답 |

---

#### 4. 결론

- 동기/비동기는 작업 처리 방식, Stateful/Stateless는 상태 관리 방식, 세션/토큰은 인증 방식으로 구분해서 이해한다.
- 필기의 두 줄은 자주 함께 쓰이던 조합을 묶어 둔 것이지, 개념끼리 정의상 연결된 것은 아니다.
- 수업의 "동기"가 "서버와 클라이언트가 상태를 맞춰(동기화해) 둔다"는 뜻이었다면 필기는 거의 맞지만, 개발 용어로 동기/비동기는 작업 처리 방식을 뜻한다.
