- `request.getSession()` 은 "내 보관함을 줘, 없으면 하나 새로 배정해줘"라는 요청이다.
- `session.setAttribute(SessionConst.LOGIN_USER_ID, user.getId())` 는 보관함에 이름표(키)와 방금 로그인한 회원의 숫자 id(값)를 넣는 코드다.
- 이 코드가 실행되는 순간 스프링이 알아서 응답에 `Set-Cookie: JSESSIONID=...` 헤더를 붙여준다. 쿠키를 만드는 코드는 따로 작성할 필요가 없다.

!image.png

- 세션에는 회원 정보 전체가 아니라 숫자 id만 저장한다.
- 메모리 최적화: 로그인한 사람이 많아질수록 세션이 무거우면 서버 메모리를 과도하게 차지한다.
- 데이터 최신화: id만 저장해두고 필요할 때마다 DB에서 다시 조회하면, 중간에 이름을 바꿔도 항상 최신 정보를 돌려줄 수 있다.

!image.png

- HTTP는 무상태(Stateless) 프로토콜이라 매 요청을 완전히 독립된 사건으로 취급한다.
- 로그인에 성공해도 다음 페이지로 이동하면 서버는 "당신이 누구시죠?"라고 다시 묻는다. 서버가 방금 일어난 일을 유지하지 않기 때문이다.
- 그래서 상태(State)를 기억할 별도의 장치가 필수적이다.

!image.png

- 물품보관함 비유로 이해한다. 로그인에 성공하면 서버가 전용 보관함을 하나 배정한다.
- 서버는 사용자를 식별할 수 있는 번호표(세션 ID)를 발급한다.
- 다음 요청부터는 매번 신분증을 보여줄 필요 없이 이 번호표만 내밀면 된다.

!image.png

| 구분 | 비유 | 위치 / 특징 |
| --- | --- | --- |
| 세션(Session) | 보관함 | 서버 쪽 저장소(Server-side) |
| 세션 ID(Session ID) | 번호표 | 사용자를 식별하는 고유 문자열 |
| 쿠키(Cookie - JSESSIONID) | 번호표를 담은 봉투 | 브라우저가 저장하고 전달(Client-side) |
| 회원 식별자(user.id) | 보관함 안의 물건 | 보관함 안에 들어가는 실제 정보 |

!image.png

- 서버가 응답에 JSESSIONID를 담아 보낸다.
- 브라우저가 이 쿠키를 자체 저장소에 보관한다.
- 이후 같은 서버로 보내는 모든 요청에 브라우저가 알아서 쿠키를 함께 보낸다. 개발자가 직접 신경 쓸 필요가 없다.

!image.png

- `request.getSession(false)` 는 세션이 없을 때 새로 만들지 않고 null을 반환한다.
- `/me`는 조회만 하는 API이므로, 로그인 안 한 사람에게 빈 보관함을 낭비하며 새로 만들 이유가 없다.
- `getSession()` 은 세션이 없으면 새로 만들고, `getSession(false)` 는 null을 반환한다.

!image.png

- 검증 코드는 `if (session == null || session.getAttribute(...) == null) { throw new IllegalStateException(...); }` 형태다.
- 성공: 쿠키가 있으면 200 OK와 함께 회원 정보를 반환한다(보관함 안의 id로 DB에서 회원 조회).
- 실패: 쿠키가 없거나 보관함이 비어 있으면 예외가 발생하고, ApiExceptionHandler를 통해 401 Unauthorized로 자동 변환된다.
- 완전히 같은 API인데 결과가 정반대인 이유는 오직 쿠키 지참 여부뿐이다.

!image.png

- 세션은 데이터베이스 테이블이 아니라 자바 프로세스의 메모리(서버 RAM)에 저장된다.
- 장점(Speed): 데이터 조회가 매우 빠르다.
- 단점(Volatility): 서버를 재시작하면 메모리에 있던 세션이 전부 사라진다.

!image.png

- 두 사람이 동시에 로그인해도 세션은 서로 섞이지 않는다.
- 서버는 각 사람이 들고 온 쿠키(세션 ID)로 보관함을 엄격히 구분한다.
- 두 세션의 ID는 완전히 다른 고유 문자열로 생성된다.

!image.png

- 로그아웃은 `HttpSession session = request.getSession(false); if (session != null) { session.invalidate(); }` 로 처리한다.
- `invalidate()` 는 보관함 안의 내용물을 비우고 번호표 자체를 폐기한다.
- 이후 같은 쿠키를 들고 `/me`를 다시 호출해도 서버가 번호표를 인식하지 못해 401 에러를 반환한다.

!image.png

- 세션 하이재킹: 다른 사람이 내 세션 ID(쿠키)를 알아내 자기 요청에 그대로 넣으면, 서버는 그 사람을 나로 착각한다.
- 공용 컴퓨터를 쓴 뒤 반드시 로그아웃을 눌러야 하는 이유다. 로그아웃(`invalidate()`)을 하지 않으면 다음 사람이 내 세션을 그대로 이어받을 수 있다.

세션 하이재킹 ?

- 공격자가 다른 사용자의 세션 ID(쿠키)를 알아내서, 그 사용자인 척 서버에 요청하는 공격이다.
- 서버는 세션 ID만 보고 사용자를 식별하므로, 유효한 세션 ID를 들고 오면 본인으로 착각한다.
- 방어 방법은 공용 컴퓨터에서 반드시 로그아웃(`invalidate()`) 하기, 쿠키에 HttpOnly·Secure 속성 주기, HTTPS 사용, 로그인 시 세션 ID 재발급, 세션 만료 시간 설정 등이다.

토큰(jwt : java web token) 이란?

- JWT는 JSON Web Token의 약자다. (기존 메모의 java web token은 잘못된 표기다.)
- Header.Payload.Signature 세 부분을 점(.)으로 이어 붙인 문자열이다.
- 서버가 상태를 저장하지 않고, 인증 정보를 토큰 자체에 담아 클라이언트가 보관한다.
- 서버는 서명(Signature)이 유효한지만 검증하므로 DB 조회가 필요 없다.

| 구분 | 세션 | 토큰(JWT) |
| --- | --- | --- |
| 상태 저장 위치 | 서버(메모리/DB) | 클라이언트(토큰 자체) |
| 서버의 상태 | Stateful | Stateless |
| 강제 로그아웃(무효화) | 즉시 가능 | 만료 전까지 어려움 |
- 서버가 어딘가에 상태를 남겨야 하는데, 방법은 크게 세션과 토큰(JWT 등) 두 가지다.
- 세션(오늘 선택): 별도 라이브러리가 필요 없고 HttpSession 하나로 구현한다. 서버가 상태를 직접 들고 있다.
- 토큰(JWT 등): 서명·검증 라이브러리가 필요하고, 서버는 상태를 안 들고 있다. 배포까지 갈 시간이 줄어든다.

!image.png

- 세션은 물품보관함에 비유한다. 로그인하면 서버가 보관함 번호(세션 ID)를 하나 내준다.
- 보관함 번호표 = 세션 ID(서버가 로그인 시 발급), 보관함 안의 물건 = 서버 메모리에 저장된 '이 사람은 누구'라는 정보, 번호표를 다시 내미는 것 = 다음 요청마다 쿠키로 세션 ID를 함께 보내는 것이다.

!image.png

- 번호표는 JSESSIONID라는 이름의 쿠키에 담겨 오고, 브라우저가 자동으로 들고 다닌다.
- 흐름은 로그인 성공(서버가 세션 하나를 만듦) → 쿠키 발급(JSESSIONID를 응답에 실어 보냄) → 브라우저 저장(다음 요청마다 자동 동봉) → 서버 확인(쿠키의 ID로 보관함을 찾음)이다.

!image.png

- 세션은 DB가 아니라 서버(자바 프로세스)의 메모리 안에 저장된다.
- 서버 메모리(오늘 방식)는 빠르지만 서버를 재시작하면 전부 사라지고, DB(선택 사항)는 느리지만 재시작해도 유지된다.
- 오늘 우리 코드는 기본값 그대로 메모리에 저장한다.

| GET /api/users/me (신규) | 지금 세션이 누구인지 확인 |
| POST /api/users/logout (신규) | 세션을 지운다 |

왜 session 방식에서 deletemapping이 아닌, postmapping인지 서치

- 일반적으로 알려진 설명을 정리한 것이며, 직접 검색해서 확인한 내용은 아니므로 강사 설명이나 공식 문서로 다시 확인해두면 좋다.
- DELETE는 URL이 가리키는 특정 자원(예: `/users/3`)을 삭제한다는 의미인데, 로그아웃은 자원 삭제가 아니라 "현재 세션을 끝내라"는 동작(액션)이다.
- 로그인(`POST /login`)과 짝을 이루는 동작 요청이라 POST로 통일한다.
- 상태를 바꾸는 요청을 GET으로 만들면 링크나 이미지 태그만으로 로그아웃되는 CSRF 위험이 있어 GET은 피한다. Spring Security의 기본 로그아웃도 POST다.
- HTML form은 GET과 POST만 지원해서 POST가 가장 다루기 쉽다.

- logout은 `invalidate()` 한 줄이면 보관함을 통째로 비운다.

#### [ UserController ]

```java
@PostMapping("/logout")
public void logout(HttpServletRequest request) {
    HttpSession session = request.getSession(false);
    if (session != null) {
        session.invalidate();
    }
}
```

!image.png

- 로그아웃하고 같은 쿠키로 `/me`를 다시 호출하면 401이 나온다.
- 쿠키 파일은 그대로인데 서버 쪽 세션이 지워졌기 때문이다.

```
curl -i -b cookies.txt -X POST http://localhost:8080/api/users/logout   # 200 OK
curl -i -b cookies.txt http://localhost:8080/api/users/me                # 401 Unauthorized
```

!image.png

## 쿠키와 세션, 세션과 토큰의 관계

- 쿠키와 세션의 관계: 세션은 서버 쪽 저장소이고, 쿠키는 그 세션의 번호표(세션 ID)를 브라우저가 들고 다니게 하는 전달 수단이다.
- 세션과 토큰의 관계: 둘 다 로그인 상태를 유지하는 방법이며, 차이는 상태를 어디에 저장하느냐다. 세션은 서버가, 토큰은 클라이언트가 들고 있다.

| 구분 | 쿠키 | 세션 | 토큰(JWT) |
| --- | --- | --- | --- |
| 정체 | 브라우저에 저장되는 전달 수단 | 서버 쪽 저장소 | 인증 정보를 담은 문자열 |
| 저장 위치 | 브라우저(클라이언트) | 서버(메모리/DB) | 클라이언트 |
| 서로의 관계 | 세션 ID를 담아 전달한다 | 쿠키의 세션 ID로 찾는다 | 쿠키나 헤더에 담아 전달한다 |

- 면접에서 자주 나오는 질문은 세션과 쿠키의 차이다.
- 세션과 쿠키는 같은 것이 아니다. 쿠키는 전달 수단이고, 세션은 서버 쪽 저장소다.
- 세션은 서버 메모리에 저장된다(오늘 우리 코드 기준).
- 로그아웃하면 서버가 `session.invalidate()`로 저장소를 비운다.

!image.png

- 실습 확인 체크리스트: 로그인 응답 헤더에 `Set-Cookie: JSESSIONID=...` 가 보이면 정상이다.
- 로그인 전 `/me`는 401 + '로그인이 필요합니다', 로그인 후 `/me`는 200 + 본인 회원 정보, 로그아웃 후 같은 쿠키로 `/me`는 다시 401이면 정상이다.

!image.png

- 실무에서는 세션을 Redis에 두기도 한다. 배운 걸 그대로 두되 저장 위치만 바꾸는 방식이다.
- Redis는 메모리 기반의 아주 빠른 외부 저장소이고, 서버가 여러 대여도 모든 서버가 같은 세션을 공유할 수 있어서 쓴다.
- 코드 구조(`getSession`, `setAttribute`)는 거의 그대로다.

!image.png

- 다음 미리보기는 상품 도메인이다. 회원 때와 똑같은 패턴이 새로운 이름(Product)으로 반복된다.
- 회원(User)은 UserController, UserService(join/login/me), UserRepository·User 엔티티이고, 상품(Product)은 ProductController, ProductService(등록/조회/수정/삭제), ProductRepository·Product 엔티티다.

- 흐름은 HTTP의 무상태 문제 → 쿠키 → 세션 → JWT → 토큰 이중화·로테이션 → 실전 트러블슈팅 → 최종 선택 가이드 순서다.

!image.png

- HTTP는 매 요청을 완전히 독립된 사건으로 취급하므로, 방금 로그인에 성공했더라도 다음 요청에서 서버는 다시 신원을 요구한다(Stateless).
- 이상적인 상태 유지(Stateful)는 요청 1(로그인), 요청 2(페이지 이동), 요청 3(장바구니 담기)이 하나로 이어지는 것이다.
- Stateless한 프로토콜 위에 State를 얹어야 하는 모순이 모든 웹 인증 아키텍처의 출발점이다.

!image.png

- 첫 번째 방식은 쿠키(클라이언트의 주머니)다. 쿠키의 발급 주체는 서버이지만 보관 주체는 브라우저다.
- 서버가 `Set-Cookie: sessionId=abc123` 으로 내려주면, 브라우저가 저장소에 보관했다가 도메인 요청 시 `Cookie: sessionId=abc123` 을 항상 자동으로 실어 보낸다.

!image.png

- 쿠키의 치명적 약점은 CSRF다. 브라우저의 '자동 전송' 특성을 악용한 공격이다.
- 사용자가 해커 사이트를 방문하면, 해커 사이트가 은행 서버로 의도치 않은 요청을 보낸다. 이때 은행 쿠키가 자동으로 동봉되므로 서버는 정상 요청으로 착각하고 승인한다.
- `SameSite=Lax/Strict` 속성으로 방어할 수 있지만, GET으로 상태를 변경하는 API가 있거나 완벽한 UX를 위해서는 한계가 있다.

!image.png

- 두 번째 방식은 세션(서버의 물품보관함)이다. 중요한 데이터는 모두 서버(메모리/DB)가 보관하고, 브라우저에는 의미 없는 랜덤 문자열(Session ID)만 열쇠로 쥐여준다.
- 쿠키는 운반 수단일 뿐이며, 서버가 생명주기를 완벽히 제어할 수 있어 `session.invalidate()` 로 강제 로그아웃을 즉시 실행할 수 있다.

!image.png

- 세 번째 방식은 JWT다(서버를 가볍게, 증명은 스스로). 서버가 아무것도 저장하지 않고(Stateless), 인증 정보를 토큰 자체에 담아 클라이언트가 보관한다.
- DB 조회 없이 토큰의 서명(Signature) 유효성만 즉시 검증하며, MSA(마이크로서비스) 환경에 최적화되어 있다.

!image.png

- JWT는 암호화(Encryption)가 아니라 인코딩(Encoding)이다. 누구나 Payload를 디코딩해서 볼 수 있다.
- Header는 알고리즘과 타입(`alg: HS256`, `typ: JWT`), Payload는 담긴 정보(`userId`, `role`)이며 디코딩하면 평문으로 노출되므로 민감 정보를 절대 넣으면 안 된다.
- Signature는 위변조 방지용으로, 비밀키(Secret Key)로 해싱된 서명이다. 이 값이 맞아야 서버가 신뢰한다. 서명의 목적은 정보 은닉이 아니라 위변조 방지(Integrity)다.

!image.png

## Stateful과 Stateless란?

- 서버가 클라이언트의 이전 요청 상태를 기억하느냐에 따라 나뉜다.
- Stateful은 서버가 상태를 저장하는 방식이다. 세션 방식이 여기에 해당한다.
- Stateless는 서버가 상태를 저장하지 않는 방식이다. HTTP 프로토콜 자체와 JWT가 여기에 해당한다.
- 관점에 따라 다르게 보인다. HTTP 프로토콜은 Stateless지만, 그 위에 세션을 얹으면 애플리케이션은 Stateful이 된다.

## Base64 란?

- 바이너리 데이터를 64개의 문자(A-Z, a-z, 0-9, +, /)로 바꾸는 인코딩 방식이다.
- 암호화가 아니라 인코딩이라, 누구나 디코딩해서 원래 값을 볼 수 있다.
- JWT의 Header와 Payload는 Base64URL(+, / 대신 -, _ 를 쓰는 변형)로 인코딩되어 있어서, 디코딩하면 평문으로 보이므로 민감 정보를 넣으면 안 된다.
- 3바이트를 4글자로 바꾸기 때문에 크기가 약 33% 늘어난다.

- 모든 아키텍처는 트레이드오프이고 완벽한 은탄환(Silver Bullet)은 없다.

| 비교 항목 | Cookie Only | Session | Pure JWT |
| --- | --- | --- | --- |
| 서버 상태 저장(State) | X | O (DB/Memory) | X (Stateless) |
| 서버 부하 / 확장성(Scale-out) | 부하 없음 | 공유 인프라 필요 | 자유로움 |
| 탈취 후 강제 무효화 | 불가 | 즉시 가능 | 만료 전까지 불가 |
| 페이로드 노출 위험 | 데이터 노출 | ID 문자열만 노출 | Base64 디코딩 노출 |
| 다중 기기 제어(중복 로그인) | 불가 | 완벽 제어 가능 | Stateless로는 불가 |

!image.png

- 토큰 이중화 전략은 무효화가 불가능하다는 JWT의 약점을 완화하기 위해 생명주기가 다른 두 개의 토큰을 쓰는 방식이다.
- Access Token은 짧은 수명(예: 15분)에 메모리/로컬 변수에 보관하며 빠른 API 요청용(Stateless)이다.
- Refresh Token은 긴 수명(예: 7~30일)에 HttpOnly 쿠키로 보관(XSS 방어)하며 Access Token 갱신 재발급용이다.
- Access Token이 만료되면 HttpOnly 쿠키의 Refresh Token을 제출하고, 새로운 Access Token을 발급받는다.

!image.png

- 토큰 로테이션 체인은 Refresh Token을 일회용으로 만들어 재사용(Replay) 공격을 방어한다.
- 정상 흐름은 사용자가 RT_1로 재발급 요청 → 서버가 RT_1 확인 → RT_1 즉시 폐기 & 새로운 RT_2 발급이다.
- 해커가 이미 폐기된 RT_1을 다시 쓰면 서버가 이를 감지하고 방어 로직이 가동되어, 해당 유저의 모든 토큰을 강제 파기하고 재로그인을 요구한다(탈취 감지).

!image.png

- 실전 트러블슈팅 1은 동시성 장애(Race Condition)다. '조회 후 없으면 생성'하는 애플리케이션 레벨의 로직은 원자적(Atomic)이지 않다.
- Request A~D가 동시에 DB를 조회하면 모두 '토큰 없음'을 반환하고, 4개가 모두 `save()`를 실행해서 DB에 중복 토큰 4개가 적재된다.
- 그 결과 `NonUniqueResultException: Query did not return a unique result: 4 results were returned` 가 발생하고 재로그인이 영구적으로 실패한다. 시험 당일 학생들의 로그인을 막아버린 치명적 장애의 원인이었다.

!image.png

- JWT의 역설: 완벽한 Stateless 토큰 인증은 이론에만 존재한다. 동시성 제어, 토큰 로테이션, 락아웃 방지, 하트비트 폴링을 구현하다 보면 세션과 토큰의 경계가 흐려지고 결국 다시 Stateful로 돌아오게 된다.
- 흐름은 Session(완벽한 Stateful) → Pure JWT(완벽한 Stateless의 꿈) → Refresh Token 도입(DB 저장 시작) → 다중 로그인/동시성 제어(Redis Lock 도입) → 결국 완벽한 Stateful 아키텍처로 회귀다.
- 해결책은 브라우저가 주기적으로 Ping(하트비트)을 발신하고, Redis TTL을 초 단위로 짧게 갱신하는 것이다.

!image.png

- 기술 선택에 정답은 없으며, '어디에 상태(State)를 저장할 것인가'에 대한 책임의 무게(Trade-off)를 이해하는 것만이 유일한 정답이다.
- 의사결정 트리: 강제 로그아웃이나 다중 로그인 제어가 필수적이면 Session 기반 구조를 선택한다.
- 마이크로서비스(MSA) 간의 인증 전파가 필요하면 JWT(Access/Refresh 이중화)를 선택한다.
- 극강의 보안과 기기 제어가 동시에 필요하면 하트비트 폴링 + 토큰 로테이션 하이브리드 아키텍처를 선택한다.
- 어떤 기술을 고를지보다, 왜 그 기술이 필요한지 이해하는 것이 먼저다.
