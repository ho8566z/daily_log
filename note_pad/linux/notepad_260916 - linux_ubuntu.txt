#### Git을 사용하는 이유

- 버전 관리
    - 코드가 변경된 모든 시점의 스냅샷(커밋)을 남겨서, 언제 무엇이 왜 바뀌었는지 추적하고 필요하면 과거 시점으로 되돌릴 수 있다.
- 협업
    - 여러 명이 같은 프로젝트를 동시에 작업해도, 브랜치(branch)로 작업을 분리하고 나중에 병합(merge)해서 충돌 없이 합칠 수 있다.
- 분산 버전 관리(DVCS)
    - 중앙 서버 없이도 각자의 로컬 컴퓨터에 전체 히스토리 사본이 있어서, 오프라인 작업이 가능하고 특정 서버가 죽어도 데이터가 안전하다.(SVN 같은 중앙집중식과의 차이점)
- 백업
    - 로컬 컴퓨터가 고장 나도 원격 저장소(GitLab 등)에 히스토리가 그대로 남아있다.

#### GitLab을 사용하는 이유

- 보안 / 데이터 통제
    - 소스코드, 이슈, 문서가 외부(GitHub 등 타사 클라우드) 서버가 아닌 회사 내부망에만 저장된다.
    - 외부 유출 위험이 낮아 금융/공공기관 등 보안이 중요한 곳에서 선호한다.
- 내부 인프라와의 통합
    - 사내 인증 시스템(LDAP, SSO 등), 방화벽, 네트워크 정책과 자유롭게 연동 가능하다.
    - 외부 인터넷 연결 없이 폐쇄망(망분리) 환경에서도 운영 가능하다.
- 커스터마이징 자유도
    - 오픈소스이기 때문에 사내 요구사항에 맞게 기능을 직접 수정/확장 가능하다.
    - CI/CD, 권한 체계 등을 회사 정책에 맞춰 세밀하게 설정 가능하다.
- 비용 통제
    - 사용자 수가 많아져도 외부 서비스 구독료 대신 자체 서버 인프라 비용으로 관리 가능하다.

## Ubuntu/Git 관련 명령어들을 상황별로 정리

#### 1. GitLab SSH 인증

| 명령어 | 설명 |
| --- | --- |
| ssh -T git@gitlab.com | GitLab과 SSH 연결 테스트 및 인증 확인 |
| ssh-keygen -t ed25519 -C "이메일주소” | 새 SSH 키 생성 |
| cat ~/.ssh/id_ed25519.pub | 공개키 내용 출력 (GitLab에 등록할 때 복사용) |
| ls -al ~/.ssh | SSH 키 파일이 이미 있는지 확인 |

#### 2. 기존 프로젝트를 내 GitLab로 옮기기 (remote 변경)

| 명령어 | 설명 |
| --- | --- |
| git remote -v | 현재 등록된 원격 저장소 주소 확인 |
| git remote set-url origin git@gitlab.com:ho8566z/shop-project-5th.git | 기존 origin의 주소만 교체 |
| git remote remove origin + git remote add origin <새주소> | 위와 동일한 효과의 다른 방법 |
| git push -u origin main | 로컬 커밋을 새 remote로 업로드 + 이후 push/pull 기본 대상으로 연결 |

#### 3. 새 프로젝트 clone/pull (Reporter 권한 등)

| 명령어 | 설명 |
| --- | --- |
| git clone git@gitlab.com:ho8566z/shop-project-5th.git | 프로젝트 전체를 새로 받기 (이때 origin 자동 등록 + main이 origin/main을 자동 추적) |
| git pull | clone받은 폴더에서 최신 변경사항만 받아오기 (별도 옵션 불필요) |
| git pull origin main | pull 대상을 명시적으로 지정하는 방식 (clone 직후엔 안 써도 됨) |

#### 4. 상태 확인용

| 명령어 | 설명 |
| --- | --- |
| git branch -vv | 로컬 브랜치가 어떤 원격 브랜치를 추적 중인지 확인 |
| git --version | git 설치 여부 및 버전 확인 |
