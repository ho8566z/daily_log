## JPA의 ORM(Object-Relational Mapping) 이란?

- 객체지향 프로그래밍의 객체(Object)와 관계형 데이터베이스의 테이블(Table)을 자동으로 매핑해주는 기술이다.
- 개발자는 SQL을 직접 작성하지 않고, 자바 객체를 다루듯이 코드를 작성하면 JPA가 내부적으로 SQL을 생성해서 DB와 통신한다.

---

## ORM(Object-Relational Mapping)의 구성 요소

#### **1. Entity (엔티티)**

- 데이터베이스 테이블과 매핑되는 자바 클래스이다.
- @Entity 어노테이션을 붙이면 JPA가 관리하는 객체가 된다.

```java
@Entity
@Table(name = "user")
public class User {
@Id
@GeneratedValue(strategy = GenerationType.IDENTITY)
private Long id;

@Column(name = "user_name")
private String name;

private String email;
}
```

| @Id | 기본키(PK) 지정 |
| --- | --- |
| @Column | 컬럼명 매핑
(생략 시 필드명 그대로 매핑) |
| @GeneratedValue | PK 자동 생성 전략 |

#### **2. EntityManager**

- 엔티티의 등록/조회/수정/삭제(CRUD)를 담당하는 핵심 객체이다.
- persist(), find(), merge(), remove() 등의 메서드 제공한다.

#### **3. 영속성 컨텍스트 (Persistence Context)**

- 엔티티를 메모리 상에서 관리하는 "1차 캐시" 같은 공간이다.
- 같은 트랜잭션 안에서는 같은 엔티티를 재조회해도 DB에 다시 쿼리를 날리지 않고 캐시에서 가져온다.
- 변경 감지(Dirty Checking): 엔티티 값을 바꾸면 별도의 update 쿼리 없이도 트랜잭션 종료 시 자동으로 UPDATE 쿼리가 나간다.

#### **4. JPQL (Java Persistence Query Language)**

- 테이블이 아닌 엔티티 객체를 대상으로 쿼리를 작성하는 언어이다.

```java
"SELECT u FROM User u WHERE u.email = :email”
```

---

#### ORM은 SQL을 없애주는 게 아니라 보이지 않게 해준다.

- JPA/ORM을 쓴다고 SQL이 사라지는 게 아니라, 개발자가 직접 SQL을 작성하지 않아도 되게 해주는 것뿐이다.
- 내부적으로는 여전히 SQL이 생성되어 DB로 전송된다.

#### **SQL이 여전히 필요한 이유**

- 복잡한 통계/집계 쿼리, 서브쿼리 등은 JPQL이나 QueryDSL, 네이티브 쿼리(@Query(nativeQuery = true))로 직접 개입해야 한다.
- 성능 튜닝(인덱스 활용, N+1 문제 해결 등)을 위해선 결국 생성되는 SQL을 이해하고 확인해야 한다.
- show-sql: true 옵션을 켜면 JPA가 생성한 SQL을 로그로 직접 볼 수 있다.

#### Persistence Context (영속성 컨텍스트)

- 영속성 컨텍스트란 엔티티를 영구 저장하기 전에 메모리에서 관리하는 논리적인 공간이다.

## JPA (Java Persistence API) 란?

## persistence 의미

- 영속성으로 "데이터를 영구적으로 저장하는 것"을 뜻한다.
- 자바 프로그램이 실행되는 동안 메모리(RAM)에만 있던 객체는 프로그램이 종료되면 사라지지만, 이를 DB에 저장하면 프로그램이 꺼져도 데이터가 남는 것을 영속성이라 한다.
- JPA는 "자바 객체를 영속화(=DB에 저장)하기 위한 표준 인터페이스(API)"라는 뜻이다.
- jpa는 데이터베이스 테이블을 자바 객체처럼 다룰 수 있는 기술이다.
- 쿼리 를 직접 작성하지 않고, 메서드 호출만으로 SQL이 자동 생성된다. (복잡한 쿼리는 JPQL/QueryDSL로 직접 작성 가능하다.)

---

| **JDBC** | 개발자가 SQL을 문자열로 100% 직접 작성 |  | 가장 저수준(Low-level) API. Connection, Statement, ResultSet을 직접 열고 닫아야 함. 반복 코드(boilerplate)가 매우 많음. 예외처리도 직접 다 처리 |  |  |  |

| **MyBatis** | SQL을 XML 또는 어노테이션에 분리해서 작성 |  | SQL과 자바 코드를 분리(SQL Mapper). 파라미터 바인딩과 결과 매핑을 자동화. SQL을 세밀하게 컨트롤하고 싶은 경우에 적합 (동적 쿼리<if>, <foreach> 등 지원) |  |  |  |
| **JPA** | SQL을 직접 작성하지 않음 (자동 생성)객체(Entity) 중심으로 코드 작성 |  | 내부적으로 SQL 자동 생성. 복잡한 쿼리는 JPQL/QueryDSL/네이티브 쿼리로 보완 필요 |  |  |  |

## EntityManager 란?

- JPA에서 엔티티(Entity)의 등록·조회·수정·삭제(CRUD)와 영속성 컨텍스트 관리를 담당하는 핵심 객체이다.
- 실제로 DB와 통신하며 엔티티를 다루는 "일꾼" 역할을 한다.

#### Entity → EntityManagerFactory(각각의 EntityManager)

!image.png

- EntityManagerFactory는 Application당 1개
- EntityManger는 스레드마다 생성
- Persistence Context는 EntityManager마다 생성하고, 1차 캐시(Entity를 저장)

## 주요기능(crud 지원)

#### persist() : 저장

- 엔티티를 영속성 컨텍스트에 등록하는 메서드이다.
- 호출 즉시 INSERT SQL이 나가는 게 아니라, 트랜잭션 커밋(또는 flush) 시점에 실제로 DB에 반영된다.(쓰기 지연, Write-Behind)
- 호출 후 해당 엔티티는 1차 캐시에 저장되고 영속(managed) 상태가 된다.

#### find() : 조회

- **PK(기본키)** 기준으로 엔티티를 조회하는 메서드이다.
- 조회 순서: 1차 캐시 확인하기 → 없으면 DB 조회 후 1차 캐시에 저장한다. → 반환한다.
- 반환된 엔티티는 영속 상태이므로 이후 필드값을 바꾸면 변경 감지(Dirty Checking) 대상이 된다.
- 데이터가 없으면 null 반환된다.(예외를 던지지 않는가. → getReference()와 차이점)

#### merge() : 수정

- 준영속(detached) 상태의 엔티티를 다시 영속 상태로 병합하는 메서드이다.
- 동작 방식: 파라미터로 받은 엔티티는 그대로 두고, PK로 DB에서 다시 조회(또는 1차 캐시 확인)한 후 그 값에 필드를 덮어써서 새로운 영속 엔티티를 반환한다.
- 주의점: merge()는 반환값을 반드시 사용해야 한다.(파라미터로 넘긴 객체 자체는 영속 상태가 되지 않는다.)
- 사실 영속 상태의 엔티티는 merge() 없이도 필드값만 바꾸면 자동 반영되므로(Dirty Checking), merge()는 주로 준영속 상태 엔티티를 다시 영속화할 때 사용한다.

#### remove() : 삭제

- 엔티티를 **삭제 상태로 전환**하는 메서드이다.
- persist()와 마찬가지로 호출 즉시 DELETE가 나가지 않고, 트랜잭션 커밋 시점에 실제 DELETE SQL 실행한다.
- 삭제 대상은 반드시 영속 상태의 엔티티여야 한다.(준영속 상태면 IllegalArgumentException 발생한다.)

| 기능 | 기존 방식 (JDBC/SQL 직접 작성) |  |  | EntityManager (JPA) |  |  |
| --- | --- | --- | --- | --- | --- | --- |
| 저장 (Create) | INSERT INTO user VALUES(...) SQL 직접 작성 후 executeUpdate() 호출한다. |  |  | em.persist(user) — 객체만 넘기면 INSERT SQL 자동 생성한다. |  |  |
| 조회 (Read) | SELECT * FROM user WHERE id=? 작성하고, ResultSet을 직접 순회하며 객체에 하나씩 매핑한다. |  |  | em.find(User.class, id) — PK만 넘기면 객체로 바로 반환한다.(1차 캐시 우선 확인) |  |  |
| 수정 (Update) | UPDATE user SET name=? WHERE id=? 직접 작성 후 파라미터 바인딩한다. |  |  | 영속 상태 엔티티는 setter만 호출 → 커밋 시 변경 감지(Dirty Checking)로 UPDATE 자동 생성한다. / 준영속 엔티티는 em.merge(user) 사용한다. |  |  |
| 삭제 (Delete) | DELETE FROM user WHERE id=? 직접 작성한다. |  |  | em.remove(user) — 엔티티 객체만 넘기면 DELETE SQL 자동 생성한다. |  |  |

## Entity 관련 주요 애너테이션

### 1. 클래스 레벨 애너테이션

| 애너테이션 | 설명 |
| --- | --- |
| @Entity | 이 클래스가 JPA가 관리하는 엔티티임을 선언. DB 테이블과 매핑되는 클래스라는 표시한다. |
| @Table(name = "user") | 매핑할 테이블명을 지정한다.(생략 시 클래스명을 테이블명으로 사용) |

### 2. 필드(PK) 관련 애너테이션

| 애너테이션 | 설명 |
| --- | --- |
| @Id | 해당 필드를 기본키(PK)로 지정한다. |
| @GeneratedValue | PK 값을 자동 생성하는 방식 지정한다. |
| ┗ strategy = GenerationType.IDENTITY | DB의 AUTO_INCREMENT에 위임한다.(MySQL에서 흔히 사용) |
| ┗ strategy = GenerationType.SEQUENCE | DB 시퀀스 객체 사용한다.(Oracle 등) |
| ┗ strategy = GenerationType.AUTO | DB 방언(Dialect)에 맞게 자동 선택한다. |

### 3. 컬럼 매핑 애너테이션

| 애너테이션 | 설명 |
| --- | --- |
| @Column(name = "user_name") | 필드와 매핑할 컬럼명 지정한다.(생략 시 필드명 그대로 매핑) |
| @Column(nullable = false) | NOT NULL 제약조건을 설정한다. |
| @Column(length = 100) | 컬럼 길이를 지정한다. (VARCHAR 등) |
| @Column(unique = true) | UNIQUE 제약조건을 설정힌다. |

### 4. 연관관계 애너테이션

| 애너테이션 | 설명 |
| --- | --- |
| @OneToMany | 1:N 관계를 매핑한다.(예: 한 유저가 여러 게시글) |
| @ManyToOne | N:1 관계를 매핑한다.(예: 여러 게시글이 한 유저에 속함) |
| @OneToOne | 1:1 관계를 매핑한다. |
| @ManyToMany | N:M 관계를 매핑한다. |
| @JoinColumn(name = "user_id") | 외래키(FK) 컬럼명을 지정한다. |

### 5. 기타 자주 쓰이는 애너테이션

| 애너테이션 | 설명 |
| --- | --- |
| @Transient | 이 필드는 DB 컬럼과 매핑하지 않는다. (일시적 필드) |
| @Enumerated(EnumType.STRING) | Enum 타입을 문자열로 저장한다. |
| @Temporal | 날짜/시간 타입을 매핑한다.(LocalDateTime 사용 시엔 보통 생략) |
| @CreatedDate, @LastModifiedDate | 생성일/수정일을 자동 기록한다.(Auditing 기능) |

!entity_to_db_flow.png

- Entity 객체: @Entity, @Id 등으로 선언된 자바 객체
- EntityManager: persist(), find(), merge(), remove()로 Entity를 관리하며 내부적으로 SQL 생성한다.
- DB 테이블: 최종적으로 SQL이 실행되어 반영되는 실제 저장소

## Persistence Context(영속성 컨텍스트) 란?

- 엔티티를 영구 저장(persist)하기 전, 메모리 상에서 관리하는 논리적인 공간이다.
- EntityManager가 생성될 때 함께 만들어지며, 엔티티를 DB에 저장/조회/수정/삭제하기 전 중간 단계에서 엔티티를 보관하고 관리하는 역할을 한다.

!image.png

**1차 캐시와 동일성 보장**

- 영속성 컨텍스트 내부에 "1차 캐시"가 있어서, 한 번 조회한 엔티티를 저장해둡니다.
- 같은 엔티티를 다시 조회(select/find)하면 DB까지 가지 않고 1차 캐시에서 바로 반환 → 조회 속도 향상.
- 같은 트랜잭션 내에서 같은 데이터를 조회하면 항상 동일한 객체(동일성)를 반환해줍니다.

---

## 영속성 이란?

- 객체(엔티티)를 데이터베이스에 저장해서, 애플리케이션이 종료되어도 데이터가 사라지지 않고 계속 유지되도록 하는 성질을 말한다..
- 자바에서 만든 객체는 기본적으로 메모리(힙)에만 존재하다가 프로그램이 끝나면 사라지는데, 이걸 DB에 저장함으로써 "영구히 보존"시키는 것이다.
- JPA는 이 영속화 작업을 객체와 테이블을 매핑(ORM)하는 방식으로 처리해준다.
- 즉 개발자는 SQL을 직접 안 짜고, 엔티티 객체를 다루는 것만으로 DB에 반영되도록 하는 게 JPA의 핵심 목표이다.

#### Persistence Context(영속성 컨텍스트)의 역할

- 엔티티를 영구 저장하는 환경이라는 뜻으로, JPA에서 엔티티 객체를 관리하는 논리적인 공간으로 실제 DB가 아니라 애플리케이션과 DB 사이에 있는 1차 캐시 같은 개념이라고 보면 된다.
- EntityManager가 엔티티를 저장하거나 조회할 때, 그 엔티티는 바로 DB로 가는 게 아니라 먼저 영속성 컨텍스트에 올라가는데, 이 컨텍스트가 엔티티의 생명주기와 상태 변화를 추적·관리해준다.

| JPA 특징 | 설명 |  | 동작 시점 / 관련 기능 |
| --- | --- | --- | --- |
| 1차 캐시 (First-level Cache) | 조회한 엔티티를 내부 캐시에 보관. 같은 ID로 재조회하면 DB 쿼리 없이 캐시에서 반환 |  | em.find() |
| 동일성 보장 (Identity) | 같은 트랜잭션 내에서 동일한 ID로 조회한 엔티티는 == 비교에서도 같은 인스턴스임을 보장 |  | 1차 캐시 기반 |
| 변경 감지 (Dirty Checking) | 영속 상태 엔티티의 값이 변경되면 별도의 UPDATE 호출 없이 변경 내용을 감지하여 UPDATE SQL을 자동 생성 |  | flush() 시 스냅샷과 비교 |
| 쓰기 지연 (Transactional Write-Behind) | persist() 호출 시 INSERT SQL을 바로 실행하지 않고, SQL을 내부에 모아두었다가 flush 시점에 실행 |  | 트랜잭션 커밋 / flush() |

## 1차 캐시

#### 캐시 란?

- 캐시는 자주 사용되는 데이터를 원본 저장소(느린 곳)보다 더 빠르게 접근할 수 있는 임시 저장 공간에 미리 저장해두는 기법이다.
- 목적: 반복적인 조회 시 비용이 큰 작업(디스크 I/O, 네트워크 통신, DB 쿼리 등)을 줄여서 성능을 높이는 것이다.
- 원리: 한 번 가져온 데이터를 메모리 같은 빠른 공간에 저장해두고, 다음번엔 원본이 아니라 캐시에서 바로 꺼내 쓴다.
- 예시: CPU 캐시, 브라우저 캐시, Redis 같은 분산 캐시, 그리고 JPA의 1차/2차 캐시

#### 1차 캐시란?

JPA의 영속성 컨텍스트 내부에 있는 캐시로, EntityManager가 엔티티를 관리하기 위해 내부적으로 갖고 있는 저장소이다.

- **핵심 특징**
    - @Id(식별자 값)를 key로, 엔티티 객체를 value로 갖는 Map 형태의 저장소
    - 하나의 트랜잭션(하나의 EntityManager) 안에서만 유효함
    - 트랜잭션이 끝나거나 EntityManager가 닫히면 1차 캐시도 함께 사라짐 (다른 트랜잭션과 공유되지 않음)
- **동작 흐름**
    1. em.find(Member.class, 1L) 호출
    2. 먼저 1차 캐시에서 해당 id가 있는지 확인
    3. 있으면 → DB에 쿼리를 날리지 않고 캐시된 객체를 바로 반환
    4. 없으면 → DB 조회 → 조회한 엔티티를 1차 캐시에 저장 → 반환

#### 2차 캐시란?

- 애플리케이션 전체에서, 여러 트랜잭션(여러 EntityManager)에 걸쳐 공유되는 캐시이다.
- 1차 캐시가 "트랜잭션 하나짜리 임시 캐시"라면, 2차 캐시는 애플리케이션이 실행되는 동안 유지되는 "전역 캐시"에 가깝다.
- **핵심 특징**
    - JPA 표준에는 개념(인터페이스 수준)만 정의되어 있고, 실제 동작은 구현체(Hibernate 등)가 제공한다.
    - 기본적으로 비활성화되어 있음 — 명시적으로 설정해야 사용 가능하다.
    - 순수 자바 힙 메모리만으로는 여러 서버 인스턴스 간 공유가 안 되기 때문에, 보통 EhCache, Redis, Infinispan 같은 외부 캐시 구현체와 연동해서 사용한다.
    - 트랜잭션이 끝나도 데이터가 사라지지 않고, 설정된 TTL(유효 시간)이나 애플리케이션 종료 시점까지 유지된다.

## Entity 동일성 보장(Identity Guarantee) 이란?

- 같은 영속성 컨텍스트 안에서, 동일한 식별자(@Id)로 조회한 Entity는 항상 같은 인스턴스(객체)임을 보장하는 것을 말한다.
- 즉 == 비교(참조 비교)로도 같다고 나온다는 뜻이다.
- 주의할 점(범위는 "같은 영속성 컨텍스트" 안에서만)
    - 동일성 보장은 하나의 트랜잭션(하나의 EntityManager) 범위 내에서만 유효하다.

## 변경 감지(Dirty Checking) 란?

영속 상태의 엔티티 필드 값이 변경되면, 개발자가 별도로 `update()` 같은 메서드를 호출하지 않아도 JPA가 자동으로 변경 사항을 감지해서 UPDATE SQL을 생성·실행해주는 기능이에요.

#### 어떻게 동작하는지?

1. **스냅샷(Snapshot) 저장**
    - 엔티티가 1차 캐시에 저장될 때(즉 em.find()나 em.persist()로 영속 상태가 될 때), JPA는 그 시점의 엔티티 값을 그대로 복사해서 스냅샷으로 함께 보관한다.
2. **flush 시점에 비교**
    - 트랜잭션이 커밋되기 직전(정확히는 flush 시점)에, JPA는 현재 엔티티의 값과 저장해둔 스냅샷을 필드 단위로 비교한다.
3. **차이가 있으면 UPDATE SQL 생성**
    - 값이 다르면 바뀐 부분을 반영한 UPDATE SQL을 만들어서 쓰기 지연 저장소에 등록하고, 이걸 DB로 전송한다. 값이 같으면 아무 SQL도 만들지 않는다.

## 쓰기 지연(트랜잭션이 끝날 때 한번에 반영) 이란?

- em.persist(), em.remove(), 엔티티 값 변경(dirty checking 대상) 같은 작업을 해도, JPA는 그 즉시 DB에 SQL을 날리지 않는다.
- 대신 실행할 SQL을 내부의 쓰기 지연 SQL 저장소(SQL Statement 저장소)에 순서대로 모아뒀다가, 트랜잭션이 커밋되는 시점(정확히는 flush 시점)에 한꺼번에 DB로 전송한다.

package com.office.calendar.member.jpa;

import com.office.calendar.member.MemberDto;
import jakarta.persistence.*;
import lombok.AllArgsConstructor;
import lombok.Builder;
import lombok.Data;
import lombok.NoArgsConstructor;

import java.time.LocalDateTime;
import java.time.format.DateTimeFormatter;

@Entity
@Table(name = "USER_MEMBER", uniqueConstraints = {@UniqueConstraint(columnNames = "ID")})
@Data
@NoArgsConstructor
@AllArgsConstructor
@Builder
public class MemberEntity {

@Id
@Column(name = "NO")
@GeneratedValue(strategy = GenerationType.IDENTITY)
private int memNo;

//    @Column(name = "ID", nullable = false, length = 20, unique = true)
@Column(name = "ID", nullable = false, length = 20)
private String memId;

@Column(name = "PW", nullable = false, length = 100)
private String memPw;

@Column(name = "MAIL", nullable = false, length = 20)
private String memMail;

@Column(name = "PHONE", nullable = false, length = 20)
private String memPhone;

@Column(name = "AUTHORITY_NO")
private int memAuthorityNo;

@Column(name = "REG_DATE", updatable = false)
private LocalDateTime memRegDate;

@Column(name = "MOD_DATE")
private LocalDateTime memModDate;

@PrePersist
protected void onCreate() {
    this.memAuthorityNo = 1;
    this.memRegDate = LocalDateTime.now();
    this.memModDate = LocalDateTime.now();
}

@PreUpdate
protected void onUpdate() {
    this.memModDate = LocalDateTime.now();
}

public MemberDto toDto() {

    DateTimeFormatter formatter = DateTimeFormatter.ofPattern("yyyy-MM-dd HH:mm:ss");

    return MemberDto.builder()
            .no(memNo)
            .id(memId)
            .pw(memPw)
            .mail(memMail)
            .phone(memPhone)
            .authority_no(memAuthorityNo)
            .reg_date(memRegDate != null ? memRegDate.format(formatter) : null)
            .mod_date(memModDate != null ? memModDate.format(formatter) : null)
            .build();

}
}

#### Optional<MemberEntity> 란?

- Java 8부터 도입된 Optional<T>는 값이 있을 수도, 없을 수도 있는 상황을 명시적으로 표현하기 위한 래퍼(wrapper) 클래스이다.
- Optional<MemberEntity>는 "MemberEntity가 있을 수도 있고, 없을 수도 있다"는 걸 타입으로 나타낸 것이다.
- JPA/Spring Data JPA에서는 주로 조회 결과가 없을 수도 있는 메서드의 반환 타입으로 많이 쓰인다.

#### 왜 MemberEntity 대신 Optional<MemberEntity>를 쓰는가?

- 기존 방식의 문제(null 반환)
    - null을 반환하는 메서드는, 호출하는 쪽에서 "이게 null일 수도 있다"는 걸 문서나 관례로만 알 수 있다.
    - 개발자가 깜빡하고 null 체크를 안 하면 바로 NullPointerException이 터진다.
- Optional을 쓰면
    - 메서드 시그니처 자체가 "이 값은 없을 수도 있으니 반드시 처리하라"는 걸 컴파일 타임에 강제하는 효과가 있다.
    - .get()을 바로 호출하면 값이 없을 때 예외가 나지만, 최소한 개발자가 "이걸 그냥 못 쓰겠구나, 처리해야겠구나"라고 인지하게 만들어준다.

| 소속 위치 | JPA/영속성 계층 (Repository, DB와 직접 연결) | 프레젠테이션 계층 (Controller ↔ View/Client) |
| @Entity 어노테이션 | O | X |
| 영속성 컨텍스트 관리 | O (1차 캐시, 변경 감지 등 대상) | X (그냥 순수 자바 객체) |
| 필드 구성 | DB 컬럼과 1:1 매핑되는 게 원칙 | 화면/API 응답에 필요한 필드만 자유롭게 구성이 가능하다.(여러 엔티티 조합 가능) |
| 변경 시 영향 | 필드 값 바꾸면 dirty checking으로 DB에 자동 반영될 수 있다. | 단순 값 객체라 변경해도 DB에 영향 없다. |
| 노출 범위 | API 응답으로 직접 내보내면 안 된다.(권장) | API 요청/응답으로 주고받기 위한 용도이다. |
